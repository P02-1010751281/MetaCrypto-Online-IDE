# 大工作区复测：218 块 / 48 过程下的 IR vs Blockly JSON（2026-11-14）

> 本文件是叙述版结论。[RESULTS-LARGE.md](RESULTS-LARGE.md) 由 `score.mjs` 生成（表格），[RESULTS-LARGE.json](RESULTS-LARGE.json) 是逐项原始分。
> 上一轮小规模实验（35 块 / 7 过程）见 [../ir-format-2026-11-14/RESULTS.md](../ir-format-2026-11-14/RESULTS.md)。
> 下一轮深度与全量见 [../ir-depth-2026-11-14/RESULTS.md](../ir-depth-2026-11-14/RESULTS.md)、[../ir-mlkem-2026-11-14/RESULTS.md](../ir-mlkem-2026-11-14/RESULTS.md)。

## 0. 为什么必须合成工作区

仓库里 60 个登记 Demo 的规模分布是断崖，不是连续谱（`MEASURED-CORPUS.md` 同口径重算）：

| 块数区间 | 工作区数 |
|---|---:|
| 0–9 | 36 |
| 10–24 | 18 |
| 25–49 | 5 |
| **50–999** | **0** |
| ≥1000 | 1（`procedures/ML-KEM-Encaps.json`，1494 块） |

也就是说「100–999 块的真实工作区」在仓库里**不存在**。要在大规模上测，只有两条路：拿唯一的 1494 块样本（单次响应装不下，见 §4），或把多个真实 Demo 的过程合成一个工作区。本实验选后者，并明确它的边界：**块树是真的，工作区是合成的**。

## 1. 任务

合并 7 份真实 Demo 的 procedure：`Goppa-Decode`(47) + `CCM-Encrypt`(35) + `PQC-Gaps`(33) + `Code-Based-Math`(32) + `Tree-Index`(25) + `ML-DSA-Primitives`(23) + `GF2m-Poly`(23) = **48 个过程 / 218 块 / 42 种块类型**。

对块树只做一处合法化改动：`GA`/`GM`/`GMod` 在 `Goppa-Decode` 与 `Code-Based-Math` 里各有一份（同工作区过程名必须唯一），故加来源后缀 `GA_GO` / `GA_CBM` 等，共 6 个定义块的 `NAME` 字段；其余块原样不动。合并集合里没有 `procedures_call*` 块，所以不存在需要同步改的引用。

给模型的输入是**格式中立**的缩进规格（`spec.md`，266 行 = 48 个标题 + 218 个块），只有类型、字段值、输入槽名与嵌套；`id`、坐标、`{"block": …}` 包装全部由模型按目标格式补。两臂的唯一差异是序列化格式：

| 臂 | 格式 | 席位 |
|---|---|---|
| A | 扁平 IR（`ciphercat.block-ir/v0`） | A1、A2 |
| B | Blockly 工作区 JSON（`blocks.blocks`） | B1、B2 |

## 2. 结果

| 运行 | 格式 | 形状 | 紧凑字节 | 块数 | id 数 | 格式缺陷 | 契约错误 | 逐过程精确 | 类型 F1 | 叶子 F1 | 整体同构 |
|---|---|---|---:|---:|---:|---:|---:|---:|---:|---:|---|
| A1 | IR | ✓ | 21 063 | 218 | 0 | **0** | **0** | **48/48** | 1.000 | 1.000 | ✓ |
| A2 | IR | ✓ | 21 063 | 218 | 0 | **0** | **0** | **48/48** | 1.000 | 1.000 | ✓ |
| B1 | JSON | ✓ | 27 456 | 218 | 218 | **0** | **0** | **48/48** | 1.000 | 1.000 | ✓ |
| B2 | JSON | ✓ | 27 078 | 218 | 218 | **0** | **0** | **48/48** | 1.000 | 1.000 | ✓ |

- **两臂全部精确复现**：48 个过程逐个与参考块树逐字相同（`逐过程精确 48/48`）；
- **跨臂同构**：`A1 ≡ A2 ≡ B1 ≡ B2`，四个产物规范化（去 id、去坐标）后是同一棵树；
- **JSON 臂的全局约束全部满足**：218 个 id 非空且互不相同、48 个顶层块带坐标、170 个嵌套块不带坐标、170 个 `{"block": …}` 包装一个不错；
- **体积**：IR 21 063 字节 vs JSON 27 078–27 456 字节，**IR 小 22.4%–23.3%**（按紧凑序列化比，不受 pretty-print 影响）；折算到每块 96.6 B vs 125.9 B。

结论直接取自预登记口径（形状正确 + 0 契约错误 + 结构等价）：**在 218 块、6.2 倍于上一轮的规模上，两种格式仍然没有可测的正确率差异；IR 唯一稳定赢下的是文本体积 −22%。**

## 3. 先导轮（v1）与它暴露的两个设计缺陷

第一次跑（产物存档在 `runs-v1/`，报告见 `runs-v1/RESULTS-LARGE.md`）结论不同：A 臂 45/48、B 臂 48/48。复盘后发现**两点都是我的实验设计缺陷，不是格式属性**：

1. **我在 A 臂格式说明里写了一句错的**：「数字型字面量也写成字符串」。于是 IR 臂把 `math_number.NUM` 从数字 `2` 写成字符串 `"2"`，命中 3 个过程（`GOPPA_INV`、`GOPPA_SYN`、`ADRS_ROOTS`）——这 3 处差异**全部**是这一句造成的；B 臂的格式说明没有这句，所以没受影响。
2. **合并工作区有 3 组重名过程**（`GA`/`GM`/`GMod`），本身不是合法工作区；v1 打分器按名字比对，48 个过程被塌成 45 个，掩盖了真实的逐过程结论。

v2 修正这两点（重命名 + 改掉那句说明）后重跑，两臂都变成 48/48。这件事本身是本次实验最可迁移的发现：**在这个规模上，一句有歧义的格式说明，杀伤力大于格式本身**——它能让一臂单独错 3/48，而两臂的真实差别是 0。

## 4. 规模上限：为什么 1494 块测不了

| 同一份 ML-KEM 工作区 | 字符数 | token（`cl100k_base` 实测） | token（`o200k_base` 实测） |
|---|---:|---:|---:|
| 扁平 IR | 90 064 | **25 484** | 26 208 |
| Blockly 工作区 JSON | 125 110 | **38 006** | 38 623 |

紧凑口径下 IR 约为 JSON 的 67%。注意这里的两条限定：**第 4 轮已实测 1494 块可以单次生成**（两席都一次写成、逐块精确），且两席实际写出 51 477 token，说明本环境的输出预算高于 32k；同时两席都把产物缩进排版（占 85% 字节），格式带来的体积优势被排版风格吃掉。详见 [../ir-mlkem-2026-11-14/RESULTS.md](../ir-mlkem-2026-11-14/RESULTS.md)。数字由 `experiments/measure-tokens.mjs` + `experiments/measure-tokens.py` 实测，明细见 [../MEASURED-TOKENS.md](../MEASURED-TOKENS.md)；tokenizer 是 OpenAI 家族公开 BPE，不是各实验席所用模型的 tokenizer，故只作量级证据。

## 5. 局限

- **每臂 2 席，且同臂产物逐字节相同**（A1 = A2 = 37 132 B）：采样方差为零，既说明任务被两臂稳定解决，也说明给不出置信区间；
- **任务是「按给定规格转写」**，不含算法推理；块树由真实 Demo 抽取，但工作区是合成的（见 §0–§1）；
- **没有加载进真实 Blockly 跑生成代码**：只做了契约校验（`validateIr` 逐块对照 `BLOCK-IO-CONTRACT.json`）与结构同构比对；
- **修复轮次未产生数据**：v2 两臂 acc@1 = 48/48，无需修复，故「修到能跑要几轮」两臂都是 0。
