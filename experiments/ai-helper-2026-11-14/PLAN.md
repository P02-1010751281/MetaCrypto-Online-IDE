## 1. 为什么先做签名表

A/B 的反向路径有两条可选路：

1. 写一个通用代码解析器（C/C++ 用 clang AST、Python 用 `ast`），再映射到块；
2. **由生成器对偶导出「代码形态 ↔ 块」的签名表**，反向解析按签名表模板匹配。

选 2 的理由：目标代码是**我们自己生成的**，形态由生成器模板决定，不是任意程序。用同一份真值（生成器）导出反向表，正向与反向永不漂移；通用解析器则会与生成器各自演化。

签名表还是三件事的共同前提：

- B1（本平台代码 → 工作区）直接靠它；
- B2（外部 C/C++ → 工作区）需要它定义「目标词汇表」；
- A 的覆盖映射需要它回答「这段语义有没有块能承接」。

## 2. 签名表怎么采（第 0 步，本轮已实现）

对 `ALL_BLOCK_TYPES` 每一个类型：

1. 在 headless Blockly 里 `newBlock(type)`；
2. 把生成器的 `valueToCode` / `statementToCode` 换成返回占位符（`@V:<槽名>@` / `@S:<槽名>@`），这样无需真实子块也能拿到该块的**代码模板**；
3. 调 `forBlock[type]`，捕获返回码与本次新增的 `definitions_`（内嵌闭包）；
4. Python 与 JavaScript 各采一遍。

产物：`out/code-signatures.json`。

它能回答的问题：

- 有多少块是叶子（模板里没有占位符，纯字段决定代码）；
- 有多少块在发代码的同时**捎带闭包**（就是 round-trip 的第一个坑）；
- 有多少模板**互相碰撞**（不同块产出同形代码 → 反解析歧义，必须额外线索消歧）；
- 哪些块直接 `getInputTargetBlock` 而不走 `valueToCode`（会在反解析时要求先有子块，顺序敏感）。

## 3.1 入口判定规则（A+B 单入口）

用户拖入一份文件后，先按内容判别，**判别结果对用户可见且可改**（一个下拉/切换，而不是静默决定）：

| 判据 | 走 A（文档） | 走 B（代码） |
|---|---|---|
| 扩展名 | `.pdf` `.md` `.txt` `.tex` `.docx` | `.c` `.h` `.cpp` `.cc` `.py` `.js` `.ts` `.rs` `.go` |
| 内容特征（无扩展名或冲突时） | 出现「标准/条款/附录/规范性」章节结构、公式块 | 出现 `#include` / `def ` / `function ` / `{}` 语句体 |
| 判别失败 | 交给用户选，并说明「我判断不了，请指定」 | 同左 |

自动判别只做「预填」，不做「锁定」——这是 owner 明确要求的形态。

## 4. 已知风险（来自实测与既有坑）

- 生成器把算法实现内嵌成数百行闭包，反解析看到的大段代码不是块产生的，必须先识别剥离。
- 浏览器内没有编译器（本机 gcc 16.2.1 / clang 23.1.4 / make 4.4.1，cmake 缺），B2 的编译差分只能走 Tauri 桌面 sidecar；Web 版只对自带官方向量的算法做语义验证。
- A 的输入大量是会变的文件（NGCC 到 2026-11 仍无定稿），必须哈希 + 版本 + 获取日期钉死。
- 模板碰撞会让「代码 → 块」多解，必须用类型/槽位做二级判别，不能靠形状。

### 写在文档里的边界

**类型自洽 ≠ 生成代码正确。** 生成器不读类型标签，检查器通过对产物零保证；判据 B 的 KAT 才是唯一能证明「错」的独立证据。领域类型（系数域 vs NTT 域）不在本轮范围，未来只做旁表推断报警告、不改接口标签。
