# 扁平 IR 是否值得保留：一次预登记对照实验

日期：2026-11-14　｜　问题：`scripts/lib/block-ir.mjs`（扁平 IR v0）是否值得继续维护？

## 0. 预登记（动手前写下，事后不改）

**假设 H1**：对于本仓库真实的「拼装」任务，模型直接产出 Blockly 工作区 JSON 会引入可测的格式缺陷（id 唯一性、坐标、`{"block": …}` 包装），而扁平 IR 会消除这些缺陷。

**判定规则**（先写后跑）：

- 若 A 组（IR）与 B 组（JSON）都做到「形状正确 + 0 契约错误 + 结构等价」，则 **H1 不成立**，IR 在该规模上没有可测收益；
- 若 A 组明显更干净（B 组出现 id/坐标/包装类缺陷且 A 组没有），则 H1 成立，IR 值得保留；
- 单臂样本若跨样本逐字节相同，则按 **N=1** 计，只报方向不报置信区间。

**指标**：形状识别、格式缺陷数、契约错误数、过程名齐全度、逐过程精确匹配、类型多重集 F1、叶子（type+fields）多重集 F1。

## 1. 材料与隔离

任务：按 NIST SP 800-38C 卡片条目，产出一个含 7 个 `procedures_defreturn` 的 CCM 工作区（`CCM_Encrypt`/`CCM_B0`/`CCM_AAD_PREFIX`/`CCM_COUNTER_BLOCK`/`CCM_CBC_MAC`/`CCM_CTR`/`CCM_Decrypt`），统一取附录 C Example 1 参数。

- 每组独立工作目录，**只**放 `task.md`、`blocks.md`（8 个块的完整端口契约 + 221 个类型清单）、`spec.json`（卡片 7 条条目含伪代码）、`format.md`（只讲本组格式）、`refs/`（同一个真实样例工作区：XTS-Encrypt，A 组是 IR、B 组是 JSON）；
- 明确禁止读取目录外文件、禁止联网；每臂 2 次独立运行（A1/A2、B1/B2）；
- 打分器 `score.mjs` 用仓库真实函数（`assembleIr` / `canonicalWorkspace` / `validateIr`）与真实参考工作区 `demos/procedures/CCM-Encrypt.json` 比对，不参与生成。

## 2. 结果

| 运行 | 预期 | 识别为 | 形状 | 格式缺陷 | 契约错误 | 过程名齐 | 逐过程精确 | 类型 F1 | 叶子 F1 |
|---|---|---|---|---:|---:|---|---:|---:|---:|
| A1 | IR | IR | ✓ | **0** | **0** | ✓ | 6/7 | 1.00 | 0.89 |
| A2 | IR | IR | ✓ | **0** | **0** | ✓ | 6/7 | 1.00 | 0.89 |
| B1 | JSON | JSON | ✓ | **0** | **0** | ✓ | 6/7 | 1.00 | 0.89 |
| B2 | JSON | JSON | ✓ | **0** | **0** | ✓ | 6/7 | 1.00 | 0.89 |

**跨臂比较**：A1 ≡ B1、A1 ≡ B2、A2 ≡ B1、A2 ≡ B2 —— 四份产物规范化后**是同一个结构**（A1 与 A2 甚至逐字节相同）。也就是说：同一模型在两种格式下不但都做对了，而且写出的是同一棵树；格式差异在结果里**不可见**。

**唯一的过程级差异**（两臂相同）是 `CCM_Encrypt`：参考工作区用 Example 3 参数（`TAGLEN=8`、24 字节消息），我个人在任务书里统一指定了 Example 1（`TAGLEN=4`、4 字节消息）。这是**我出题口径**与仓库 Demo 的差异，不是模型的错误，也不是格式的差异。

按预登记规则：**H1 不成立**。

## 3. 确定性测量（不涉及模型）

### 3.1 语料里的「拼装」到底有多大

| 指标 | 值 |
|---|---|
| Demo 工作区 | 60 个（2151 块 / 148 个 procedure） |
| 单 procedure 块数 | 中位数 **4**，p90 **7**，最大 **1494** |
| ≤3 块的 procedure | **40 / 148** |
| <25 块的工作区 | **54 / 60** |
| ≥100 块的工作区 | **1 / 60**（ML-KEM-Encaps，1494 块） |

### 3.2 两种格式必须产出的内容（同一工作区）

| 工作区 | 块数 | IR 字节 | JSON 字节（组装后） | 差 | 必须全局唯一的 id 数 | 键/节点 IR → JSON |
|---|---:|---:|---:|---:|---:|---|
| CCM-Encrypt | 35 | 3 382 | 4 290 | −21% | 35 | 2.57 → 3.97 |
| ML-KEM-Encaps | 1494 | 90 105 | 128 911 | −30% | 1494 | 同上 |

外加：JSON 每个输入槽与 `next` 都要包一层 `{"block": …}`（CCM 样例 28 个、ML-KEM 规模约 1 200 个）。

> **口径说明（重要）**：本表的「IR 字节」由 `flattenWorkspace(doc, 文件名)` 得出，含一个 `source` 键；「JSON 字节（组装后）」是 `assembleIr` 的输出（自动生成 id 与 `{"block": …}` 包装），**都不是**「模型实际要写的紧凑文本」。同一工作区按「模型实际输出」口径的紧凑对照是 **IR 90 064 字符 / JSON 125 110 字符**（ML-KEM）、**3 343 / 4 728**（CCM），见 [../MEASURED-TOKENS.md](../MEASURED-TOKENS.md)。两组数不可互相换算或混用。

### 3.3 天花板

- ML-KEM 那份 1494 块的工作区，IR 约 90 KB（`cl100k_base` 实测 **25 484 token**）、JSON 约 126 KB（实测 **38 006 token**，见 [../MEASURED-TOKENS.md](../MEASURED-TOKENS.md)）。当初按 3.5 字符/token 粗估写成「≈2.3 万 / ≈3.2 万」，实测后 JSON 一侧被低估约 6k。紧凑口径下 IR 约为 JSON 的 67%。**第 4 轮复测已推翻这里的施工结论**：1494 块可以单次生成，两席都一次写成且与真实文件逐块精确，且实测输出 51 477 token——说明本环境的输出预算不是 32k（详见 [../ir-mlkem-2026-11-14/RESULTS.md](../ir-mlkem-2026-11-14/RESULTS.md)）。
- 而 IR 真正能帮上忙的区间（几十到几百块、需要人肉盯 id 一致性的规模），在本仓库里只有 5 个工作区（25–47 块）。

## 4. 结论

1. **可测收益为 0**：在仓库真实的拼装规模上（procedure 中位数 4 块），IR 与 JSON 的表现完全一致，跨臂结构逐字节等价；
2. **机械收益真实但很小**：每节点少 1.4 个键、文本少 21–30%、去掉 N 个全局唯一 id 与 N 个包装对象；但唯一的大样本（1494 块）在实测中两席都选择了缩进排版，实际输出 51 477 token（紧凑形式 25 484），缩进 85%——体积收益被排版风格吃掉（第 4 轮实测）；
3. **成本是确定的**：642 行（lib 227 / schema 60 / 门禁 233 / 测试 78 / 声明 44）+ 仓库第五种表示（TS 定义、workspace JSON、BLOCK-IO-CONTRACT.json、IR），且 v0 不支持 shadow/注释；
4. **没有生产者**：`spec:scaffold` 产出的是 `block.ts` + 双生成器 stub，不产 IR——这个格式至今没有任何一条真实生产链在写它。

**当时的建议**（已被 2026-11-14 的大工作区复测修正，见 §7）：删除 IR、只保留契约校验。那份建议的前提是「IR 在任何规模上都不赢」；复测在 218 块上测到两条新数据（体积 −22%，以及最大真实样本实测 25.5k vs 38.0k token 的容量差），前提不再成立，故当前结论是**冻结保留、不追加投资**，而不是删除。

保留它唯一有价值的那半——**契约校验**（1641 块逐块对照 `BLOCK-IO-CONTRACT.json`）——这件事与「留不留 IR」独立：即使保留 IR，这段校验也值得能脱离 IR 单独跑。

## 5. 局限（必须一起读）

- **有效样本 N=1/臂**：同臂两次运行逐字节相同，说明采样方差为零，这既降低了噪声，也意味着不能给出置信区间；
- **任务难度偏低**：7 个过程各由 1 个黑盒块完成（这正是仓库 Demo 的真实形态），没有触及深嵌套；
- **打分口径**：语义分是「与参考工作区的结构重合度」，不是正确率——同一标准义务可以有多种合法拼法；
- **未执行**：没有把产物加载进真实 Blockly 跑生成代码（那需要构建产物，成本高于本次实验的收益）；契约校验已覆盖端口/类型层面的一致性。

## 7. 后续复测：大工作区（2026-11-14）

本实验的任务只有 35 块，而仓库里 50–999 块的真实工作区是 0 个（分布见 [../ir-large-2026-11-14/RESULTS.md](../ir-large-2026-11-14/RESULTS.md) §0）。复测把 7 份真实 Demo 合成 218 块 / 48 过程的工作区，结论：

- 两臂（IR / Blockly JSON）都 **48/48 精确复现、0 格式缺陷、0 契约错误、跨臂同构**——在 6.2 倍规模上仍无正确率差异；
- IR 的文本体积小 **22%–23%**（21 063 B vs 27 078–27 456 B）；
- 唯一对 IR 有利的容量数据：用 `cl100k_base` 实测，ML-KEM（1494 块）IR **25 484 token** vs JSON **38 006 token**（[../MEASURED-TOKENS.md](../MEASURED-TOKENS.md)），第 4 轮已在 1494 块上实测：两席单次生成成功、逐块精确，且实际输出 51 477 token（紧凑 25 484），说明「32k 上限」这一前提不适用于本环境；
- 先导轮（v1）曾出现 A 臂 45/48，复盘确认是**我给 A 臂写的一句歧义格式说明**造成的，不是格式属性（详见该报告 §3）。

因此本文件的「删除」建议已被修正为「冻结保留、不扩功能、P1 立项时用 ML-KEM 级任务复测」。
